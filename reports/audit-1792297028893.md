# Button check-up: web app + mobile app

I went through the code behind every screen in FLOW — about 100 screens on the web side plus the mobile app (which is really the same web app loaded inside the iPhone/Android shell) — looking for buttons that are wired up wrong: buttons that do nothing when tapped, links that lead to a page that doesn't exist, "Pay," "Send," and "Save" buttons that silently fail, and the handful of known trouble spots that have bitten this app before. The good news: I didn't find any dead or broken buttons. Every link I checked points to a real page, and every "Save/Send/Sync" button I checked is wired to real, working code. I did find one spot worth tidying up before it causes a real problem — the standalone invoice "Pay Now" button uses its own separate copy of the payment code instead of the one shared, battle-tested copy the rest of the app uses.

### The standalone-invoice "Pay Now" button has its own private copy of the payment code
- **What's happening:** When a client pays one of your one-off invoices (not tied to a specific inspection's balance-due), that "Pay Now" link runs its own separate version of the Stripe payment setup, instead of using the single shared piece of code the rest of the app uses for every other payment button (the inspection balance-due "Pay Now" in the client portal, and the payment reminder emails). Right now this copy does the right thing — it still sends the money to your own connected account and still adds your online-payment fee correctly — but it's a second, hand-maintained version of logic that has caused real money bugs before (an earlier bug sent money to the wrong account and skipped the fee, which is why the shared version exists in the first place).
- **Why it matters to you:** It works today, but it's the kind of thing that quietly breaks later — if the payment logic ever gets updated in the one "official" place (to fix a fee issue, add a new payment type, etc.), this second copy won't get that fix automatically, and a future standalone-invoice payment could charge the wrong fee or go to the wrong account without anyone noticing until a client complains.
- **How urgent:** Worth doing eventually — nothing is broken right now, but it's a loaded gun sitting on the table for the next payment-related change.
- **Where it is:** The "Pay Now" button on a standalone invoice (the kind you create from the Invoices page, not tied to a specific inspection) — (`app/api/invoices/[id]/checkout/route.ts`, versus the shared helper at `lib/stripeCheckout.ts`).
- **What I'd do:** Have the builder route standalone-invoice payments through the same shared payment helper the rest of the app uses, instead of keeping a second copy.

---

**What else I specifically checked and didn't find problems with:**
- Every "Save," "Send," "Sync," "Copy link," and "Sign" button I sampled across settings, reports, invoices, agreements, and the field-capture (mobile) screen is wired to a real function — no blank or placeholder buttons.
- Every link/button that takes you to another page (over 150 of them) points to a page that actually exists — no "page not found" dead ends.
- The three specific database landmines that have broken buttons/emails in this app before (findings table, photos ordering, email log numbers) are not present anywhere in the current code — those past fixes are holding.
- The mobile offline-sync "Sync Now" button correctly stays enabled when there are failed items waiting to retry, so a field inspector with a flaky connection can always retry.
- The App Store subscription rules are respected — the app correctly shows Apple's in-app purchase button instead of a Stripe button when running inside the iPhone app.

**One honest limitation:** this was a read of the code, not a live click-through on a phone or in a browser (that wasn't part of what I was asked to do here). Code that's wired correctly can still behave oddly on an actual device — e.g., camera/microphone permission prompts, spotty signal in the field — so if you want extra confidence before a release, a quick real-device pass on the field-capture screen (photo, voice note, offline sync) is the one area I'd spot-check by hand.
