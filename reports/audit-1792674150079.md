# FLOW App Checkup — Oct 22, 2026

I went through the app end to end, with extra time on the report builder since that's what you asked about. The good news: the private-report-link protections, the login/no-login boundaries, and the actual money-handling code all check out fine. I did find one AI feature that's been quietly not doing what it's supposed to since it was built, a small visual glitch in the report builder from Monday's "screen jumping" fix, and one spot where the same payment math is written out twice, which is a risk for later, not now.

## Findings

### The "write like you" AI feature has never actually worked
- **What's happening:** When the AI writes up a finding for you — in the report builder, the AI Camera, or the live inspection camera — it's supposed to first look at a handful of your own past published reports, so the wording it generates sounds like how you actually write. That lookup fails every single time, because it asks the database for a piece of information off the wrong table — one that doesn't have it. The failure is swallowed quietly: no error shown to you, your inspectors, or even in the background logs.
- **Why it matters to you:** The AI write-ups you and your inspectors have been getting have never actually been tuned to sound like your voice — that part of the feature has been pure placebo since it shipped. It's not dangerous, but it's a real feature you (or inspectors) may have assumed was working and wasn't.
- **How urgent:** Fix soon — no risk to data or money, but it's silently not delivering a feature you have.
- **Where it is:** the AI writing assistant used across the report builder, AI Capture, and the live inspection camera (`lib/ai/findingRetrieval.ts`)
- **What I'd do:** point that lookup at the inspector who owns the inspection (via the inspection record) instead of a field the findings table doesn't have.

### Running "AI Inspector" on two findings quickly makes the status messages pile on top of each other
- **What's happening:** Monday's fix stopped the little "working…" / "saved" message from pushing the page up and down — it now floats at the bottom of the screen instead. But that message is tracked separately for every finding, and the floating box always appears in the exact same spot. If you run the AI Inspector note on one finding, then move to a different finding and run it again before the first message disappears (a few seconds later), both messages show up stacked directly on top of each other at the bottom of the screen.
- **Why it matters to you:** You'd see a jumbled, hard-to-read pair of messages for a few seconds and not be able to tell which finding each one is about. It's just confusing, not dangerous — nothing gets lost or overwritten.
- **How urgent:** Fix soon — cosmetic, but it's on a screen you and your inspectors use constantly.
- **Where it is:** report builder, the "Run AI Inspector" button on an individual finding (`app/reports/[id]/ReportFindingsSortable.tsx`, `components/EditableFinding.tsx`)
- **What I'd do:** have each message stack slightly offset from the others (or only show the newest one) so they don't land in the same spot.

### Two different places build an online payment page, with the fee math written out twice
- **What's happening:** When a client pays their inspection balance through the client portal, that payment page is always built the same well-documented way, in one shared place. Standalone invoices (one-off bills not tied to a balance due) go through a second, separate piece of code that recalculates the same card-processing fee and rebuilds its own payment page instead of reusing the first one.
- **Why it matters to you:** Both work correctly today. But if you or a developer later change how the card fee works — who pays it, what percentage — there's a real chance only one of the two gets updated, and the two payment flows quietly start disagreeing with each other.
- **How urgent:** Worth doing eventually — it's a future-risk issue, not a current bug.
- **Where it is:** standalone invoice payment links (`app/api/invoices/[id]/checkout/route.ts`) duplicate the logic that inspection balance-due payment links already use (`lib/stripeCheckout.ts`)
- **What I'd do:** have the invoice payment link reuse the same shared payment-building code that inspection balances use, instead of its own copy.

## What I checked and didn't find problems with

- The rule that the `findings` table can't take an "inspector" owner column, and the rule that `email_logs` needs the numeric inspection number in a specific field — both are respected everywhere I found, except for the one AI lookup above.
- Photo/video ordering in reports and PDFs — the database was updated to support it, and the ordering code was only turned on after that update went live, so nothing is at risk of photos silently disappearing.
- No-login client links (shared reports, agreements, the homeowner maintenance hub, payment-return pages) — all still reachable without forcing a login, and all still gated by their private link rather than a guessable ID.
- Recently shipped features (the "one signature covers everyone on the deed" option for agreements, requiring login before importing a report, scoping saved checklist options/comment library to each inspector) all look correctly built with no leftover gaps.
- Cautious wording rules for report write-ups (never predicting a hard failure date on a component) are actively enforced in the AI prompts.
- The offline capture queue on the iPhone app still stores photo/video data the way that survives an app restart, as it's supposed to.
