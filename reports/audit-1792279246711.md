# FLOW codebase audit — top 3 risks

Read-only audit. No application code or config was modified.

## 1. [SECURITY — HIGH] Unauthenticated IDOR on the homeowner portal via sequential inspection id
**Where:** `app/my-home/[token]/page.tsx` (~lines 128–141), route is public per `proxy.ts:66` (`/my-home` in `PUBLIC_PREFIXES`, no login wall).

The page resolves the inspection by `public_share_token` first, but if that lookup misses and the URL segment is all-digits, it falls back to:
```ts
.from("inspections").select("*").eq("id", lookup).maybeSingle()
```
with **no ownership, session, or auth check anywhere in the file** (confirmed — no `auth.`/`getUser`/`cookies` calls besides comments). This directly violates the project's own rule to "gate the raw sequential-id path."

**Failure scenario:** Anyone requests `/my-home/1`, `/my-home/2`, … and gets back a complete stranger's home: equipment inventory, findings (section/severity/title), maintenance plan, and inspector/company name — a straightforward cross-tenant data leak with no credentials required.

## 2. [CORRECTNESS/MONEY — MEDIUM-HIGH] Duplicate Stripe checkout path bypasses the shared helper
**Where:** `app/api/invoices/[id]/checkout/route.ts` (~lines 44–184) vs. the documented single source of truth `lib/stripeCheckout.ts`.

`lib/stripeCheckout.ts` exists so every inspection payment "always pays the SAME way" (Connect direct-charge + online fee, with a `stripe_logs` insert for reconciliation). The invoice checkout route instead calls `stripe.checkout.sessions.create` directly with its own re-implementation of the Connect-blocker check and fee math, and never writes to `stripe_logs`. Invoices can carry an `inspection_id` and get stamped into `metadata.inspection_id`, so these look like ordinary inspection payments everywhere except the one table used for revenue reconciliation.

**Failure scenario:** A future fix to fee computation, Connect-blocker logic, or metadata shape applied only in `lib/stripeCheckout.ts` silently does not apply to invoice-driven payments; any report or reconciliation job reading `stripe_logs` undercounts real revenue tied to inspections, with no error or alert.

## 3. [PERFORMANCE — LOW-MEDIUM] Sequential, un-batched token-column probes on a hot, latency-constrained PDF route
**Where:** `app/api/realtor-report-download/[id]/route.ts` (~lines 2429–2450), `maxDuration = 300`.

On every request the route runs up to three sequential `SELECT *` + `.maybeSingle()` queries against `inspections` (one per legacy token column) before it even starts the Puppeteer render, instead of a single query with an `OR` filter across the candidate columns.

**Failure scenario:** Each download pays 1–3 extra serial DB round-trips ahead of an already slow render pipeline that the code's own comments say has previously hit timeout limits; under repeated/concurrent downloads this compounds tail latency on the route with the least time budget to spare.

---
*Verified as currently correct and not re-flagged:* `findings` inserts never include `inspector_id`; `email_logs` inserts consistently use `inspection_id_bigint`; `photos.sort_order` is backed by a real migration — the documented gotchas in CLAUDE.md are respected elsewhere in the codebase today.
